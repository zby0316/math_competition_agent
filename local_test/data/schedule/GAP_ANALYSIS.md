# 差距分析报告：Intern-S2 数学智能体 vs 顶尖方案

> 评估对象：挑战杯 Intern-S 数学智能体（Intern-S2-Preview-397B API，112 题/6h/并发 3/单题 1200s，仅官方 API，无训练，无 Lean）
> 评估依据：`nodes/sc_consensus_node.py`、`nodes/cross_validator_node.py`、`utils/answer_verifier.py`、`utils/competition_methods.py`、`local_test/data/schedule/round_log.md`、`V46/V42_DESIGN.md`，以及 `local_test/results/` 下各轮实测数据
> 日期：2026-08-26

---

## 0. 执行摘要（TL;DR）

1. **机制不缺，缺的是"可信验证"与"预算纪律"**。你们已经把 AIMO2 的 SC+早停、IMO25 的验证-精炼、InternLM-Math 的交错推理都移植了一遍，方向正确；但全部机制建立在一个**同源不可靠的验证器**上（验证代码也是 397B 写的），导致"双 PASS 锁错"（deep_water_iter #0：对错误答案 2 双验证 PASS，官方是 3）。验证器不可信 → 投票/仲裁/精炼全部被污染，这是机制层的第一短板。
2. **成绩轨迹核实后比表面更严峻**：本地各轮（同一 LLM 判分口径）74.1% → 62.2% → 48.6% → 49.1% → 40.2% → 39.3%，官方同题集 V2.5.8 = 54.46%（且 V2.5 官方曾达 61.61，V2.5→V2.5.8 官方**回退了 7 分**）。本地判分比官方宽松 ~20pp（round1 本地 74.1% vs 官方 54.46%，同版本同题集）——**本地轮次分数不可外推官方，V3.4~V5.3 机制分支至今未过官方评测**。
3. **差距归因：约 1/3 机制可救，2/3 模型不可救**。用你们自己的攻坚实验量化：47 道深水区错题上，SC 救回 5/47、交错推理 2/46、双验证攻坚 1/47、代码 1/35，去重后约 7/47（~15%）；其余 85% 是 397B 同源同错/推理深度不足，采样再多也救不回（V46 设计文档自己承认"42 题仍错：模型单次推理在这些题上就是错的"）。
4. **官方约束下现实天花板 ≈ 63-67%**（机制再挤 +3~6 分），超过 70% 需要换更强模型或训练，机制救不了。你们预期的 59-65% 是**乐观但可达**的——前提是回到"确定性证据优先"的路线，而不是继续堆 LLM 采样/仲裁。
5. **预算正在失控**：round6 实测 155,741 API 秒 = 官方并发 3 下 14.4h，超 6h 预算 2.4 倍（config.py 注释自认）；V5.3 的调用硬上限（easy≤10/medium≤16/hard≤24）是补救但不是免费——它同时压缩了机制火力。**预算再分配（减 LLM 仲裁、增确定性执行）比新增机制更值钱**。

**四个必须写进结论的事实**：

1. **官方分数从 V2.5 (61.61) 回退到 V2.5.8 (54.46)**：机制分支（V3.4~V5.3）从未进过官方评测，而 V2.5→V2.5.8 之间的改动在官方同题集上已经 -7 分。**"新版本更好"在官方口径下没有被证明过**。
2. **本地判分比官方宽松 ~20pp**（round1 同版本同题集：74.1% vs 54.46%）。round6 本地 39.3% 若按同口径外推，当前 V5.3 管线在官方题集上可能只有 ~45-55%，**可能低于 V2.5 的 61.61**——机制膨胀没有带来官方收益的证据。
3. **轮次之间难度不对等**：round1-3 全新题（easy 占比高），round4-6 错题重测残渣占比上升（round6 重测 67/112，hard 47%），分数下滑部分来自题更难。但即便如此，**机制在更难集上没有把残渣啃下来**（round4→6 平台期 39-49%）。
4. **round6 里 SC 共识节点实际从未生效**（sc_consensus_done=0，节点 0.0s）：39.3% 是没有 SC 的成绩。而官方模拟运行（`set1_official_sim.json`，进行中 50/112）里 SC 每次触发平均吃掉 ~183s/题、10/50 题预算出现负剩余——**SC 要么没跑，要么跑起来就烧预算，两头都没得分**。

## 2. 机制深度对比（逐项 vs 顶尖方案）

| 机制 | AIMO2 金牌（~90%+） | rStar-Math（90% MATH500） | IMO25 验证-精炼（银牌级） | **本项目现状** | 差距定性 |
|---|---|---|---|---|---|
| **采样 (Sampling)** | 20-50+ 候选/题，**以代码生成为主**，执行成功即过滤，纯确定性投票 + 早停（k 个一致即停） | MCTS 每节点多采样，PRM 引导 | 多候选生成 + 形式化验证过滤 | SC：6 视角推理 + 3 份代码 + 交错，**以 LLM 采样为主**（round6 avg 23.5 次 API 调用/题，官方 V2.5 仅 11.5） | **数量级差 5-10×，且方向反了**：我们把预算花在 LLM 生成上，AIMO2 花在廉价执行+确定性过滤上 |
| **验证 (Verification)** | **程序即答案**：数值题直接让程序算，答案=执行输出，无需二次验证 | 代码执行 + 结果核对作为 PRM 训练标注 | **Lean 形式化验证**（穷尽、无假阳性） | 验证器也是 397B 生成的代码；双 PASS 才锁；PASS 须带数值对照证据 | **同源确认偏误未根除**：求解和验证是同一个模型，会"一致地错"（deep_water_iter #0 双 PASS 锁错、round3 回放 6/6 双闭式同错） |
| **搜索 (Search)** | 采样+投票（无步骤级搜索，靠规模） | **MCTS + 训练 PRM** 逐步打分、回溯 | 验证-精炼循环（每次反馈修正） | 无步骤级搜索；mcts_experiment（beam×4）自评打分恒为 5、无区分度，未进主图 | **无过程奖励**。无训练前提下，LLM 自评步骤质量不可用（实验已证明），需要换成"代码可验证的步骤"做启发 |
| **反思/精炼 (Refine)** | 验证失败丢弃重采样 | 验证失败反例回注训练 | **验证反例 → 下一轮生成**（核心循环） | verifier_feedback 存在（FAIL→反例→下轮），但验证器本身不可靠 → 反馈是噪声，且 deep_water 轮间递减采样（9→5→4） | **循环成立的前提（可信验证器）缺失**，精炼变成"强化错误答案"（#0 被双 PASS 确认后锁定） |
| **分解 (Decompose)** | 隐式（代码分步） | 步骤级 MCTS 天然分解 | 问题自动分解为子目标 | 无显式分解；SC 视角（代数/构造/枚举）只是**浅层方法提示**，不是步骤计划 | AgentMath/PólyaMath 的"计划-执行-回顾"缺位，深题缺结构 |
| **过程奖励 (PRM)** | 无（靠结果投票） | **训练 PRM**（自生成数据） | Lean 判定即过程奖励 | 无；LLM 自评 1-5 分无区分度 | 无训练约束下无法获得真 PRM，只能退化为"可执行步骤"启发 |
| **早停 (Early stop)** | k 个**执行成功且一致**的答案即停 | 节点置信收敛 | 验证 PASS 即停 | 2/3 文本/闭式一致即停 | **一致 ≠ 正确**（同源），早停会快速锁错；AIMO2 的早停建立在"执行成功"这个真实信号上 |
| **预算纪律** | 计算为主，LLM 调用少 | 搜索预算显式分配 | 每题长时但 Lean 验证廉价 | round6 API 秒 = 6h 预算的 2.4 倍（155,741/64,800）；V5.3 调用硬上限 ≤1,700 次 | **预算结构错配**：LLM 仲裁/重算/调解链吃掉大头，确定性执行只占小头 |

**一句话结论**：你们缺的不是"机制的零件"（零件都装了），缺的是两个承重墙——**可信的验证器**（决定性证据）和**以执行为主体的采样策略**（廉价算力替代昂贵 LLM 调用）。顶尖方案的全部优势都可以归结为这两点；你们的全部失分也可以归结为这两点。

## 3. 差距量化：模型能力 vs 机制

### 3.1 三个硬数字

1. **机制救回上限（用你们自己的实验）**：47 道深水区错题上，SC 5/47、交错 2/46、双验证攻坚 1/47、代码主解 1/35、MCTS-beam ~0，去重后 **~7/47（15%）**。这是"重测仍错的最难子集"上机制能挤出的全部。
2. **本地-官方判分差 ~20pp**（round1 同题集同版本 74.1% vs 54.46%）。意味着本地任何"提升 N 分"的实验结论，在官方口径上都要打大折扣；你们 round2 本地 67% → 官方从未验证，V2.5 官方 61.61 是唯一被官方证实的峰值。
3. **round6 难度分布正确率**：easy 5/10=50%、medium 23/48=47.9%、hard 16/53=30.2%。**easy 只有 50% 是巨大信号**——397B 对简单题也会错，且这些错误大部分是"机制可救"的（廉价多采样几乎必中）；hard 30% 是模型能力天花板在起作用（所有机制叠加后仍只有 1/3）。

### 3.2 归因估算

以"官方同题集 112 题"为基准（V2.5 官方 61.61 → 顶尖方案在同题集的理论 ~90% 级，但注意 **AIMO2 的 90% 不可直接对比**：AIMO2 只有 40 题、以数值可验证题为主、可用旗舰模型+海量代码采样；本挑战是 Omni-MATH 风格大学级混合题 + 397B 固定模型）：

| 差距来源 | 占比估计 | 依据 |
|---|---|---|
| **模型能力**（397B vs 旗舰：算术可靠性、长链推理深度、组合/几何洞察） | **~60-70%** | hard 30% 正确率 + 85% 深水区模型不可救 + easy 50% 里也有一部分是 397B 的"会做但算错" |
| **机制执行缺口**（验证器不可信、SC 未生效、预算错配、仲裁链低效） | **~20-25%** | 机制实验救回 7/47（15%）+ round6 SC 从未触发 + 官方 -7 分回退中有一半可归因于工程回归 |
| **判分/格式/工程损耗**（本地-官方 20pp 差、截断、串题、放弃型答案） | **~10-15%** | V2.5 截断根治/结论先行等修复确实在官方 +2 题（59.82→61.61） |

### 3.3 诚实的结论

- **模型是主瓶颈**：~2/3 的差距在 397B 本身，机制救不了。深水区 47 题里 40 题"采样多少次都是同一个错"——这是模型知识/推理上限，不是采样策略问题。
- **机制不是无用的，是没生效**：SC 在 round6 一次都没跑（sc_done=0），验证器会锁错（#0），交错推理只救 2/46——**现有机制的实际收益远低于其设计收益**，修复执行缺口比发明新机制收益更大。
- **本地实验的"救回 N 题"不可直接外推官方**：同题集本地-官方差 20pp 决定了，本地实验只适合做"相对排序"（哪个机制好），不适合预测官方分。

### 4.1 预算账本（先算清楚再谈机制）

| 指标 | 数值 | 官方预算 | 结论 |
|---|---|---|---|
| round6 API 秒总量 | 155,741s | 6h×并发3 = 64,800s | **超 2.4 倍** |
| round6 平均每题 | 23.5 次调用 / 498s 墙钟 / 1391 API 秒 | 单题 1200s 硬限 | 每题已用到 40%+ 预算 |
| official_sim（V5.3 进行中） | avg 378s/题，SC 平均 183s/触发题，10/50 题负剩余 | — | SC 是预算黑洞，且部分题已超软预算 |
| V5.3 调用硬上限 | easy≤10/medium≤16/hard≤24，全卷 ≤1700 | — | 补救措施，但压缩了机制火力 |

**推论**：在官方约束下，你**没有预算**再堆任何新的 LLM 密集机制。任何"加机制"的建议都必须以"减 LLM 调用"为对价。

### 4.2 天花板分解

| 情形 | 官方预期 | 依据 |
|---|---|---|
| 现状（V5.3 机制分支，未过官方） | **45-55%**（可能低于 V2.5 的 61.61） | round6 本地 39.3% + 本地-官方 ~20pp 差 + SC 未生效 + 预算超支风险 |
| 回归 V2.5 已证实的能力（截断根治/结论先行/答案渲染） | **~61-62%** | 官方实证（V2.5 = 61.61） |
| + 修复执行缺口（SC 真正生效、验证器去同源、预算再分配、easy/medium 廉价多采样） | **~64-67%** | 机制实验 7/47（15%）× 错题池 + easy/medium 错题廉价救回 |
| 超过 70% | **不可达**（机制层面） | 需更强模型（旗舰推理模型）或训练（rStar-Math 式 PRM 训练被"无训练"约束排除） |

**机制可救 vs 模型不可救的边界**：
- **可救**（~10-12 题/112）：easy/medium 错题中的"会做但错"（多采样必中）、验证器锁错造成的假错、SC 未触发导致的漏救、预算超支导致的未完成。
- **不可救**（~35-40 题/112）：hard 深水区中 85% 的同源同错——397B 在这些题上的单次正确率 ~30%，且所有采样共享同一个知识/推理上限（n 份采样救回率 = 1-(1-p)^n，p≈30% 时 6 份也只有 88%……但实验实测只有 15%，说明这些题 p 远低于 30%，多数接近 0）。

## 5. 三个最重要的机制升级建议（可落地、合规、预算内）

> 原则：**每一分预算从 LLM 生成/仲裁挪向确定性执行**；**每一个锁必须建立在执行证据上**，而不是模型自评/文本一致。

### 建议 1（最高优先级）：验证器去同源化 —— 把"验证"从 LLM 生成改为"随机实例对照 + 题面独立重算"

**问题**：`utils/answer_verifier.py` 的验证代码由 397B 生成，与求解同源，会"一致地错"（deep_water_iter #0 双 PASS 锁错 2≠3；round3 回放 6/6 双闭式同错）。当前"双独立代码 + PASS 须带数值证据"只缓解了表面（防无对照 PASS），没解决根因（对照本身是同一个模型算的）。

**改法**（全部零训练、纯 API+sympy，合规）：
1. **验证器提示注入"禁止使用候选答案参与任何计算"**——现有 `_VERIFY_PROMPT` 已声明但执行代码经常违反（"把候选代入题面验证"本身就是用候选）。改为强制"**从题面条件重新建模求解目标**，只在最后一步与候选数值比对"。
2. **随机实例对照**：对含参数/通项的题，验证代码必须在**随机生成的 N 个实例**上独立计算并与候选闭式的实例化值比对（容差 1e-6 / Fraction 精确），而不是只验证题面那一个数字。单个数字的 PASS 可能是"蒙对"，N=20 个随机实例一致才接近真证据。
3. **符号健全性预检**：候选闭式先过 sympy 化简一致性（同一表达式两种化简路径结果一致）+ 数值抽样（5 个随机点数值一致）——**成本 ~0**（本地 sympy），能挡掉大部分"形式漂亮但数值错"的候选。
4. **弱验证永不锁**（已做，V5.0-fix3）+ **双 PASS 也只在"随机实例对照"成立时锁**（新增）。

**预算**：验证器每次 ~2 次调用，不增加调用次数（把现有 2 份验证代码的 prompt 改掉即可）；随机实例对照跑在本地执行器，几乎免费。

**预期收益**：round3 回放 6/6 同错、#0/#7/#110 类锁错题是本管线"最贵的错误"（错得自信、直接出厂），这类题在每轮 112 题里估计 8-15 题，去同源后按保守一半救回算 **+4~7 分/轮**。这是性价比最高的一笔。

### 建议 2：代码优先（Code-First）主解 + 执行过滤投票，替代"LLM 仲裁/重算"链

**问题**：round6 每题 23.5 次调用，其中 semantic_arbiter 经常 abstained/skipped、reconciliation 整轮重跑（每题 2-3 次完整 reasoning+python）——LLM 仲裁在"两候选都错"时选不出对的（round3 回放 9/12 选错），纯烧钱。

**改法**（AIMO2 金牌路线的可落地版）：
1. **对计算类题（已能路由，`state_is_rule_judgeable`/特征词），把"仲裁前重推"替换为"3-5 份独立代码求解"**：brute/sympy/dp/数值模拟/蒙特卡洛 各 1 份，执行成功的代码结果做数值等价投票；≥2 份一致 → 锁定（无需 LLM 仲裁）。这复用现有 `sc_consensus_node` 的代码通道，但**把它从"推理不一致才跑"改成"主验证路径"**，并优先于 reconciliation。
2. **删/降级 LLM 仲裁**：semantic_arbiter 只在"代码全不可用 + 候选是文本/证明"时才启用；计算题冲突一律 playoff → 双代码 → 投票，三级都是确定性证据，最后才轮到仲裁。
3. **早停信号换成"执行成功"**：2/3 文本一致不足以停；改为"2 份独立代码执行成功且数值等价"才停（AIMO2 的 early stopping 语义）。

**预算**：一次仲裁 ~1-2 次调用、一次 reconciliation 重推 ~6-10 次调用；一次代码投票 ~3-5 次调用（生成代码）+ 执行免费。**每题省 3-6 次调用**，全卷省 ~400-600 次——正好把 round6 超支的 2.4 倍压回 6h 内，省下的预算给建议 1 和建议 3。

**预期收益**：round4-6 里 playoff 后仍不可决进仲裁/重算的题每轮 ~20-30 题，其中代码投票能确定性解决的保守 ~1/3 → **+2~4 分/轮**；同时把墙钟从 5.2h 压回 <4h，消除 6h 超时风险（超时即 0 分，这是隐性的最大失分源）。

### 建议 3：按难度重配采样预算 —— easy/medium 错题多采样，hard 只做"可验证步骤"的交错推理

**问题**：round6 easy 50%、medium 47.9%——简单题错一半，而 SC 的触发条件（未 match + 计算类 + remaining>600s）在 easy 上经常不触发（match 即出厂，同源同错直接锁错出厂，#0/#29 实证）；预算却全花在 hard 的深水区（救回率 15%）。**预算分配与边际收益倒挂**。

**改法**：
1. **easy/medium 出厂前必过"一次廉价复核"**：match 出厂前（`enable_match_reverify` 已有雏形）对 easy/medium 一律做 1 次独立短采样（~45s，温度 0.3，prefill 短答案），一致才出厂；不一致进 SC。成本：easy≤10/medium≤16 的调用上限内完全放得下。
2. **hard 只保留"可执行步骤"路径**：交错推理（已救 2/46，是唯一实证的新通道）从"SC 之后才跑"提前到"hard 首路径失败即跑"，但**每步必须输出可执行代码**（语言步骤不单独计预算）；纯推理视角采样从 6 份降到 2 份（deep_water 实验表明视角采样的边际收益在第 3 份后趋零）。
3. **SC 触发门修正**：round6 SC 从未生效的根因要查清（触发条件 `remaining_hard > 600` + `validation_status not in (match, None)` + 计算类判定，三者在实际运行中极少同时成立）——**要么放宽 easy/medium 触发（建议 3.1 已覆盖），要么在 `give_up_forced_sc` 之外增加"match 但双代码可判"触发**（V42 设计里的 A 类：同源同错风险题）。

**预算**：净增 ~1 次调用/题（easy/medium），净减 ~4 次调用/题（hard 视角采样缩减）——**总调用下降**，与建议 2 叠加后全卷 ≤1500 次，墙钟 <4h。

**预期收益**：easy/medium 错题池每轮 ~30 题，廉价复核按 40-60% 救回率 → **+3~5 分/轮**。

## 6. 三个建议的预期合计与落地顺序

| 建议 | 官方预期收益 | 预算影响 | 落地难度 | 顺序 |
|---|---|---|---|---|
| 1. 验证器去同源化 | +4~7 分 | ≈0 | 低（改 prompt + 判定逻辑） | **先做** |
| 2. Code-First + 砍仲裁 | +2~4 分（并消除超时风险） | -400~600 次调用 | 中（改路由 + 复用 SC 代码通道） | 第二 |
| 3. 预算按难度重配 | +3~5 分 | -200 次调用 | 低（改触发条件） | 与 2 并行 |
| **合计** | **官方 54.46 → 64~67** | **全卷 ≤1500 次调用，墙钟 <4h** | — | — |

**配套动作**：
1. **先修回归再谈提升**：V2.5 官方 61.61 → V2.5.8 官方 54.46 的 -7 分回退要逐版本回放定位（V2.5→V2.6→V2.5.8 的改动里一定有负贡献项）；机制分支（v33）先回放官方同题集确认不低于 V2.5 再谈加分。
2. **本地实验只做相对排序**：任何"救回 N 题"都要记同题集官方对照（round1 的 74.1% vs 54.46% 是唯一校准锚点），不要用本地绝对分决策。
3. **SC 全链路排查**：round6 sc_done=0 是执行缺口实锤——新机制写了但没跑，等于没做。
4. **official_sim 运行注意**：当前 V5.3 官方模拟运行（50/112 进行中）是机制分支第一次可对标的成绩，跑完判分后再定最终提交版本；若其判分低于 54.46，官方提交应**回退到 V2.5 或修复后的 V5.3**。

## 7. 一句话总结

你们的机制零件是齐全的，但**三个承重墙是空的**：验证器同源不可信（锁错）、SC 没真正生效（白写）、预算花在 LLM 仲裁上而不是确定性执行上（超支 2.4 倍）。把这三处修好，官方 54.46 → 64-67 是现实可达的；再往上（70%+）是 397B 的模型天花板，机制救不了——**诚实地说，这轮挑战的正确目标是"守住 V2.5 的 61.61 并逼近 65"，而不是追 AIMO2 的 90%**（那是不同的题、不同的模型、不同的预算结构）。
