# 官方评测成绩最大化配置建议（V5.x 定稿版）

> 目标环境：官方评测 112 题 / 6h 墙钟 / 并发 3 / 单题 1200s / Intern-S2-Preview-397B API。
> 本文所有数字均来自 `local_test/results/` 实测数据与 `config.py` / `nodes/sc_consensus_node.py` 现行参数，
> 每个阈值都标注了依据与性价比权衡。
> 生成时间：2026-08-26 · 基于 v33（V5.2 末态）+ round6（2627 调用/轮）实测。

---

## 0. 一句话结论

**官方分预期 61–66%，中枢 ≈ 63%；** 决定性变量不是"深水区多救几道"（官方只抽 ~1.2 道/轮），
而是 **6h 墙钟内能不能跑完全部 112 题**（round6 调用量 155,741 API 秒 = 官方并发 3 下 14.4h，
超 6h 上限 2.4 倍——不压调用量，一切机制归零）。预算纪律第一，机制精度第二。

## 1. 调用预算分配（问题 1）

### 1.1 官方 6h 的真正硬约束是 API 秒，不是调用次数

| 量 | 数值 | 来源 |
|---|---|---|
| 6h 墙钟 | 21,600 s | 官方规则 |
| 并发 3 下的 API 秒总预算 | **64,800 s**（21600×3，理想满载） | 推导 |
| 官方 API 单次调用实测 | **≈31 s**（1288 次 / 3h41m / 并发 3） | V2.5.8 官方日志 |
| 官方 API 慢速估计 | ≈35 s/次 | config.py 注释 |
| round6 实测 API 秒 | 155,741 s（2627 次，均值 59.3 s/次） | set1_round_006_graded.json |
| round6 → 官方并发 3 折算墙钟 | **14.4 h**（155741/3） | 推导（超限 2.4×） |

**结论：官方并发 3 下，全卷 API 秒预算 = 64,800 s。** 这是唯一硬约束；
"单题 1200s"只是单题上限，墙钟约束先到先死。

### 1.2 每题可用调用数上限

| 场景 | 公式 | 全卷调用上限 | 每题均值 |
|---|---|---|---|
| 零余量（满载 6h） | 64800 / 31 s | ≈2,090 次 | ≈18.7 次 |
| 留 15% 余量（5.1h） | 64800×0.85 / 31 | ≈1,776 次 | **≈15.9 次** |
| 按 35 s/次 + 15% 余量 | 64800×0.85 / 35 | ≈1,573 次 | ≈14.0 次 |

**建议全卷调用量目标 ≤1,700 次（每题均值 ≤15 次）**，这是"官方 6h 必然跑完"的安全线。
round6 实际 2,627 次 → 需压缩 **~35%**。

### 1.3 按难度分配（官方题集分布：easy≈30% / medium≈45% / hard≈25%）

官方分布来源：`round_manager.py BAND_WEIGHT = {easy: 0.30, medium: 0.45, hard: 0.25}`，
112 题 ≈ 34 easy / 50 medium / 28 hard。round6 实测各难度调用（含深水区拖累）：

| 难度 | round6 均值（次/题） | 建议上限（次/题） | 建议目标（次/题） | 全卷预算（目标×题数） |
|---|---|---|---|---|
| easy | 15.3 | ≤10 | **8** | 34×8 = 272 |
| medium | 21.2 | ≤16 | **14** | 50×14 = 700 |
| hard | 26.8 | ≤24 | **20** | 28×20 = 560 |
| 深水区（≈1.2 题） | — | ≤35 | ≤30 | ~36 |
| **合计** | 23.5 | — | **≈15.0** | **≈1,570 次** ✓ |

加权校验：0.30×8 + 0.45×14 + 0.25×20 = 2.4+6.3+5.0 = 13.7（再加深水区 ~1.2 题×30 ≈ 36 次 → 全卷 ≈1,570 次），
按 31 s/次 = 48,670 API 秒 = **4.5h 墙钟**，留 1.5h 给 API 波动（铁律⑨）。

### 1.4 配套改动

- `config.py max_llm_calls_per_problem`：26 → **easy 10 / medium 16 / hard 24**（按难度动态取 cap，`TimeBudget` 支持构造时传入）。
- `difficulty_soft_budgets`：现状 easy 480 / medium 840 / hard 1200 合理，**保留**（软预算只影响可选阶段，不动硬限）。
- `paper_total_seconds`：18000（5h 目标）保留——PaperPacer 落后判定用 1.15 倍系数，5h 目标 + 1h 缓冲已是最优。
- **SC 阶段预算封顶（V5.1 已实现）必须保留**：`sc_end = max(400, remaining_hard - 400)`，保 coordinator 收尾。

## 2. 各机制触发阈值建议（问题 2）

### 2.1 SC 共识（`nodes/sc_consensus_node.py`）——触发条件微调

**round6 实证**：60 题触发 SC，37 题有采纳（其中 12 题正确 = 采纳精度 32.4%）；
hard 题 SC 触发组正确率 39% vs 未触发组 12%（SC 对 hard 是 3 倍增益）；
每次触发平均仅 +3.5 次调用（采样均值 3.3 份：2.7 推理 + 0.6 代码）。**SC 性价比高，保留全火力。**

| 参数 | 现值 | 建议值 | 依据 |
|---|---|---|---|
| 触发硬条件 | 未 match + 规则可判定/计算特征词 + remaining_hard>600s | **保留**（easy 也触发，V5.1-修正2） | round6 easy 50% 主因是 SC 关闭，V5.2 已回滚 |
| `remaining_hard` 触发下限 | 600s | **700s**（hard）；easy/medium 维持 600s | 6 采样×31s + 验证器 2×31s ≈ 250s，600s 下验证器必被砍 |
| 早停 | 2/3 一致即停 | **保留** | round6 均值 3.3 份就停，成本可控 |
| 推理采样数 | 6 视角 | **hard 6 / medium 4 / easy 3** | 6 视角救回 7/47（+40%），但 easy 命中率高，3 份足够 |
| 代码采样数 | 3 算法 | **hard 3 / medium 2 / easy 1** | 代码通道 round6 均值仅 0.6 份/触发（早停），easy 无需 3 份 |
| 散文接管 | 主链路非闭式 + SC 唯一闭式 → 锁 | **保留** | round5 #10 实证 |

### 2.2 双验证（`cross_validator` / V4.7 通用 Python 双验证）

- **现状**：python 闭式 + 与推理冲突 → 强制第二独立代码，双代码等价才锁。
- **round6 实证**：这是"错题重测救回率 6.4%→23.9%"（3.7 倍）的主因。
- **建议**：触发条件 **放宽**——不限于"冲突"，**凡主链路答案非闭式（散文/放弃）且有 python 闭式候选时也强制双验证**（当前只对冲突触发，放弃型漏网）。代价约 +1 次调用/题，收益是 #24/#44 类假性放弃的确定性兜底。
- `cross_validator` 超时 15s→30s：保留。

### 2.3 放弃重读（`reasoning_agent_node` V4.5）

- **现状**：解析出放弃型答案 → 强制一次"逐字重读题面"重推（不含旧答案防锚定），`_reread_used` 只触发一次。
- **round6 实证**：#24/#13/#14/#110 类（easy/medium 模型会做但坚称条件不足）；round6 仅 1 题漏网（#13）。
- **建议**：
  - 重读仍放弃 + **规则可判定** → 强制 SC（V5.2 `give_up_forced_sc` 已实现，保留）；
  - 重读仍放弃 + 非计算题 → 出厂"部分求解"（V2.3 hard_fallback，保留）；
  - **新增**：放弃重读对 easy 题只给 **1 次**（现已是），medium/hard 维持 1 次——多轮重读边际收益 < 调用成本。

### 2.4 程序化验证器（`utils/answer_verifier.py` V4.9）

- **现状**：SC 投票未决 → 对 top-2 候选各生成 2 份独立验证代码（最多 4 次调用），双 PASS 才锁；PASS 须带数值对照证据（防同源确认偏误）。
- **round6 实证**：错锁归零（V5.0-fix3 #110 修复）；#0/#34 被确定性确认锁定（47 道最难题）。
- **建议触发门**：
  | 条件 | 现值 | 建议值 |
  |---|---|---|
  | 仅验证闭式候选 | ✅ | 保留 |
  | 剩余硬时间下限 | 200s | **≥500s**（验证器 2×2 次 ≈ 120s + coordinator 收尾） |
  | top-2 → top-1 降级线 | 无 | 剩余 <700s 时只验证 top-1（省 2 次调用） |
  | 弱验证（1 PASS + 1 INCONCLUSIVE） | 不锁 | **保留不锁**（fix3 教训） |

### 2.5 出厂防线（V4.5）与 6h 风险

- 跑题拦截（#16 类）、假性放弃跳过仲裁（#24/#44 类）、SC 散文接管：**全部保留**，零成本、零误伤（265 测试全绿）。
- **最高优先防线 = 调用量上限**：`max_llm_calls_per_problem` 按难度生效后，紧急直答（`emergency_answer`）仍豁免（现逻辑保留）。

## 4. 预期官方成绩（问题 4）

### 4.1 模型：按官方难度分布加权

官方分布（34 easy / 50 medium / 28 hard）+ 各难度实测正确率：

| 难度 | round6（V4.x，深水区拖累轮） | round2（V3.x，官方模拟） | V5.x 期望（SC 恢复+双验证+交错） |
|---|---|---|---|
| easy | 50%（n=10） | 80%（12/15） | **78–82%** |
| medium | 47.9%（23/48） | 66.7%（38/57） | **66–72%** |
| hard | 30.2%（16/53） | 48.7%（19/39） | **48–55%**（SC+验证器+交错） |

> round6 的 39.3% 是 **hard 占 47% 的深水区重测轮**，不是官方分布；
> round2 的 67% 才是官方模拟分布（35% hard）下的成绩。V5.x 在官方分布下应显著高于 round6。

**加权期望（V5.x，本地判分口径）**：
0.30×0.80 + 0.45×0.69 + 0.25×0.51 = 0.24 + 0.3105 + 0.1275 = **67.8%**（≈ 76/112，与 round2 67% 同口径、略升）。

### 4.2 官方判分折扣

V2.5.8 官方实测：本地 61.61% → 官方 54.46%（差 7.15pp，官方 judge 更严/版本差异）。
按此折扣：67.8% × (54.46/61.61) ≈ **59.9%**；保守取 **60–63%**。

### 4.3 深水区影响（官方抽题 ~1.2 道/轮）

- 深水区 44–47 道 = 397B 能力上限，各机制合计救回率 ~15–20%（7/47 SC + 1/47 迭代 + 2/46 交错，含重叠）。
- 官方抽中 1.2 道 → 期望失分 ≈ 1.2 × (1−0.17) ≈ **1.0 道 ≈ 0.9pp**。
- 计入后：**官方预期 59–65%，中枢 ≈ 62%**；若交错入图再捞回 0.5–1 道 → **61–66%，中枢 ≈ 63%**。

### 4.4 风险敏感性（必须向用户说明）

| 场景 | 触发 | 官方分 |
|---|---|---|
| 调用量压到 ≤1,700 | 预算纪律生效 | **61–66%** |
| 调用量维持 2,600 | 墙钟 14.4h → 后 40 题超时无答 | **~35–45%**（完成率 60–70%） |
| API 慢到 40s/次 + 不压量 | 同上更甚 | ~30% |
| 官方 judge 比本地严 8pp | 超预期 | 下限 −2pp |

## 5. 提交前最后 3 个最高性价比改动（问题 5）

### 改动 1（最高优先）：调用量按难度硬上限落地
- `config.py max_llm_calls_per_problem: 26 → {"easy":10, "medium":16, "hard":24}`
  （`TimeBudget` 已支持构造传入；`llm_retry.py` 已按 cap 快失败→确定性兜底）。
- 全卷目标 ≤1,700 次（4.5–5.0h），消除 6h 超时这个**唯一能归零一切机制**的风险。
- **依据**：round6 2627 次 / 155,741 API 秒 = 官方并发 3 下 14.4h（见 1.1 表）。

### 改动 2（最高收益）：交错推理入图（SC 第 7 路采样）
- 把 `local_test/deep_water_solver.py::_interleaved_solve`（1 次，≤4 步，逐步代码执行反馈）搬进
  `nodes/sc_consensus_node.py`，作为推理 6 视角之后的第 7 路（预算门：remaining_hard > 700s 才跑）。
- **依据**：#46/#62 是 SC/代码/管线全部失败、仅交错救回的新路径（2/46）；成本 1–4 次调用，
  官方每轮多救 ~0.5–1 道 ≈ +0.5–0.9pp，是提交前唯一"确定性新增"的救回通道。
- 注意复用图内 MCP 执行（`deps.mcp_client`）而非 subprocess（官方沙箱合规）。

### 改动 3（低投入高确定性）：验证器触发门收紧 + 双验证覆盖放弃型
- 验证器：`remaining_hard < 700s` 只验 top-1（省 2 次/题）；`< 500s` 不跑（现值 200s 太激进，验证器 120s 会挤占 coordinator 收尾）。
- 双验证：触发条件从"与推理冲突"扩到"主答案非闭式 + 有 python 闭式候选"（放弃型也有机器证据，防 #24/#44 重读后再放弃出厂裸猜）。
- **依据**：V5.0 错锁归零（fix3 #110）+ #0/#34 确定性确认，验证器是"锁对"的最后一道闸；上述微调只改触发线，不改逻辑，测试零回归风险。
