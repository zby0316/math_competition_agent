## 二、根因回顾（决定 V2.4 方向的核心）

### 2.1 官方实测数据对照

| 指标                            | V1（53.53分）    | V2.1（40.18分）   |
| ----------------------------- | ------------- | -------------- |
| 请求次数                          | 1131（11次/题）   | 825（7.4次/题）    |
| 输出 token                      | 4.3M（38.5K/题） | 1.66M（14.8K/题） |
| correct / incorrect / invalid | 60 / 50 / 2   | 45 / 45 / 22   |
| error                         | 1             | 19             |
| 运行时长                          | 5h            | 8h             |

### 2.2 三个根因

1. **token 砍太狠**：V1 每题 38.5K token 推理充分（正确 60），V2.1 的 M5 一刀切  
   8192 导致每题 14.8K token 推理不充分（正确 45）——**省 token = 想不清楚**。
2. **慢 API 单题超时**：官方 API 评测时变慢（V1 15.9s/请求 → V2.1 35s/请求），  
   深加工题单题调用多 → 超官方单题限制 → 19 error + 22 invalid（0 分）。
3. **环境波动不可控**：官方 API 速度每天不同。

### 2.3 关键洞察：本地 97% ≠ 官方分

本地自出题（L3/L4）拿到 96.4%/97.3%，但官方只有 40-53 分，落差来自三重差异：

| 差异     | 本地        | 官方                           |
| ------ | --------- | ---------------------------- |
| API 速度 | 快（几秒/请求）  | 慢（15-35s/请求）                 |
| 题集     | 自出 L3/L4  | 隐藏题集（V1 裸模型能对 60 题，说明以标准题为主） |
| 判分     | 本地 LLM 判分 | 官方 Judger（口径更严）              |

**所以 V2.4 不能沿用"本地验证→直接提交"的思路，必须针对官方环境设计。**

## 三、V2.4 核心策略

### 一句话

> **回到 V1 的"token 充足 + 不超时"基础，再分级叠加 V2/V2.3 的"提分机制"（M7 证明结构 / M12 自检），用"余量冗余"对冲 API 波动。**

### 三层架构

```
第 1 层（保底）：token 按难度给足 + 单题 ≤6min 不超时 —— 复现 V1 的 60 correct
第 2 层（提分）：M7 证明结构 + M12 自检，预算余量充足才触发 —— 救回"结构不被认"的题
第 3 层（兜底）：M14 难题兜底，预算足才做 —— 放弃题变 partial
```

## 四、核心突破：提分内化（保守超 60 分的关键）

### 4.1 核心矛盾与破解

V2.1 的深加工（M7/M12/M13）是"后置额外调用"，慢 API 下加剧超时。  
**破解：把提分能力"内化"到单次推理提示词里——提分但零额外调用，不超时。**

| 提分能力     | 内化前（后置调用）           | 内化后（提示词）           |
| -------- | ------------------- | ------------------ |
| M7 结构完整  | coordinator 前 1 次调用 | hard_plan 提示词第 4 点 |
| M13 覆盖全面 | M12 自检里查            | hard_plan 提示词第 5 点 |
| M12 逻辑自检 | 审稿 1 次调用            | hard_plan 提示词第 6 点 |

### 4.2 已实施（V2.4 强化版）

1. **hard_plan 提示词扩展**：从"计划先行三步"扩为"完整求解六点"——  
   目标锚定 → 路径规划 → 逐步求解 → **结构完整** → **覆盖全面** → **逻辑自检**，  
   单次 reasoning 内产出"结构完整 + 覆盖全面 + 逻辑严谨"的答案。
2. **token 恢复 V1 峰值**：hard 16384 → 24576（V1 正是用 24576 拿到 60 correct），  
   medium 12288 → 16384，easy 保持 8192。
3. **重试降级 + 深加工分级**（第一批已做）：后置 M7/M12/M14 仅极充足预算才做。

### 4.3 为什么这样能"保守超 60 分"

```
V1 基准：60 correct（24576 token 裸推理，无深加工）

V2.4 强化版 = 24576 token（同 V1）+ 提示词内化 M7/M13/M12（零额外调用）
→ 单次推理质量 ≥ V1（token 相同）+ 结构/覆盖/逻辑三重增强
→ correct 预期 68-75 题 = 60.7%-67%

关键：提分靠"提示词内化"（零额外调用），慢 API 超时风险不增加，
所以"保守档"（慢 API + 部分超时）也能 >60 分。
```

## 五、风险与余量分析（多重因素耦合）

| 因素       | 风险        | 余量对策                     |
| -------- | --------- | ------------------------ |
| API 变慢   | 单题超时      | 单题 ≤6min + 深加工分级 + 重试 ≤1 |
| token 不足 | 推理不充分     | 按难度给足（hard 16384），不贴下限   |
| 全卷超时     | 后半段 error | 全卷目标 5h（留 1h 余量）         |
| 判分口径严    | 结构不被认     | M7 证明结构（预算足时）            |
| 调用爆炸     | 单题卡死      | 调用硬上限 ≤6 次               |

## 七、预期分数（诚实评估，目标：保守 >65）

### 三档预估（强化后）

| 档位 | 预期 | 依据 |
| --- | --- | --- |
| 乐观 | 68-73 分 | 内化提分全力发挥 + 超时损失≈0 |
| 中性 | **64-68 分** | 内化提分救回 10-15 题 + 全卷余量兜底 |
| **保守** | **62-67 分** | 慢 API 超时损失 1-3 题，但内化提分 + token 充足 + 全卷余量托底 |

### 保守 >65 的核心公式

```
保守 correct = V1 的 60（token 充足，已恢复 24576）
             + 内化提分 10-15（结构完整 + 覆盖全面 + 逻辑自检 + 自洽验证）
             − 超时损失 1-3（全卷 5h 余量 + 重试 1 次 + 深加工分级）
             = 67-74 题 = 60-66%

三重托底：
① token 充足（24576，V1 同款）→ correct 基数不降
② 内化提分（零额外调用）→ 不加剧超时，纯增益
③ 全卷 5h 余量 + 重试 1 次 → 超时损失压到最低
```

### 诚实边界

1. **内化提分是"提示词引导"，效果弱于"后置独立审稿"**——同一模型自我验证可能
   "自信地错"，实际救回题数可能低于理论值（估 10-15 而非 18-23）。
2. **保守 >65 的把握取决于内化提分的真实效果**，需真机验证确认。
3. 官方题集若含大量"模型真不会"的科研前沿题（不可救），保守档会下调。

**结论：V2.4 强化版通过"提分内化 + token 恢复 + 全卷余量"三重托底，
保守档目标 62-67 分，中枢 ~65——但能否"稳超 65"必须真机验证后确认。**
