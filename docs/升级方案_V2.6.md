# V2.6 升级方案（3 版备选 + 自审）——2026-08-20

> 背景：V2.5 官方实测 61.61 分（69/112，历史最佳），但 truncated=203（14.5%）
> 暴涨 + 请求 1402（+57%）+ 墙钟 3h53m（6h 的 65%）。续写雪球是头号问题，
> sympy 短路 1% 命中是第二问题。三版方案按"改动量从小到大"给出。

## 方案 A：外科手术式修复（P0 聚焦，最小改动）

**目标**：消除截断雪球 + max_tokens 摸底，稳定 69 → 71-73 题。

| # | 动作 | 文件 | 改动量 |
|---|---|---|---|
| A1 | `truncation_continue_tokens` 2048 → 4096（按难度分级：easy 4096 / hard 8192） | config.py | 1 行 |
| A2 | `truncation_continue_max_rounds` 2 → 1（一次续写不够就直接走压缩重试，不再循环累积截断计数） | config.py | 1 行 |
| A3 | `_looks_truncated` 弱信号写满判据适配：官方可能 clamp max_tokens，判据从 `>= max_tokens*1.5` 改为 `>= min(max_tokens, 4096)*1.5`（防本地判据与官方实际不符导致漏判） | llm_retry.py | 2 行 |
| A4 | 压缩重试触发条件收紧：仅主调用异常或**已确认截断**时触发，正常完成不触发 | llm_retry.py / reasoning 节点 | ~5 行 |
| A5 | client_probe 摸底：本地 pip 装 lagent==0.5.0rc3，用官方同款 client 验证 thinking_mode/max_tokens 真实透传；确认是否 clamp，结果写 trace | utils/client_probe.py | ~30 行 |

**收益**：
- 截断 203 → ~90（-55%），请求 1402 → ~1050（-25%），墙钟 3h53m → ~3h
- 每次续写 4096 足够覆盖"答案尾部"，一次续完，不再雪球
- max_tokens 摸底后可按官方实际值配置，根治"答案超预算"误判

**风险**：极低。纯参数 + 2 处逻辑微调，不碰架构。
**验证**：本地小批 20 题（重点看截断题是否一次续完）→ 全量 112 题（可选）→ 提交。
**耗时**：2-3 小时。

## 方案 B：截断治理 + sympy 自然语言化（P0 + P2）

**目标**：方案 A 全部 + 让 sympy 真正接管可计算题（1% → 10-20%），冲 73-75 题。

| # | 动作（在 A 基础上追加） | 文件 | 改动量 |
|---|---|---|---|
| B1 | sympy 中文自然语言模式扩展：`求 (\d+)\^(\d+) 除以 (\d+) 的余数` / `求 (\d+)x≡(\d+) (mod|模) (\d+)` / `求 f(x)=... 的导数/不定积分` / `求 \d+ 的 \d+ 次幂` | utils/sympy_pre_solver.py | ~40 行 |
| B2 | python_agent sympy 验证结果反哺：交叉验证时若 python 分支 sympy 确定性算出且 LLM 答案为空/明显异常 → 用 python 结果作为候选参与仲裁 | nodes/cross_validator_node.py | ~20 行 |
| B3 | 自然语言识别命中统计：pre_solve 命中写 trace（`sympy_nl_hit`），便于下一轮评估 | utils/sympy_pre_solver.py | ~5 行 |

**收益**：
- A 的全部收益 + sympy 从 1% → 10-20% 命中（估算 10-20 题被 sympy 秒解或硬校验）
- 计算题（同余/模幂/积分/极限）正确率从 ~90% → ~99%（确定性）
- 潜在 73-75 题（65-67 分）

**风险**：中。sympy 本身不会算错，但**"识别错题"风险**——中文正则匹配到非目标题会给出"确定性错误答案"（比 LLM 猜错更隐蔽）。必须：识别要求严格锚定（关键词 + 数字形态 + 无歧义），且保留"python 验证分支兜底"（sympy 答案与 LLM 答案冲突时走 playoff）。
**验证**：需要 30+ 条中文题用例覆盖识别/拒绝两类；112 题全量重跑对比正确率。
**耗时**：5-7 小时。

## 方案 C：请求链路全面重构（激进）

**目标**：单题请求数硬上限 + 统一 token 预算，把墙钟压到 2.5h 内。

| # | 动作 | 改动量 |
|---|---|---|
| C1 | 单题请求数硬上限（15 次），超限走确定性兜底 | ~40 行 |
| C2 | 重试/续写/压缩/仲裁统一预算入口（TokenBudget 全局记账） | ~60 行 |
| C3 | 续写与压缩重试合并为单一"截断挽救"通道 | ~50 行 |
| C4 | 低置信度仲裁路径降级（仲裁只对 mismatch 且时间充足时启用） | ~20 行 |

**收益**：墙钟 2.5-3h、请求 900-1000、最坏情况可控。
**风险**：**高**。动核心链路（重试/仲裁/预算），回归风险大；验证周期长（全量 112 题 + 边界用例）；与提交窗口（今晚 24:00）冲突。
**耗时**：2-3 天。

## 自审结论

| 维度 | A | B | C |
|---|---|---|---|
| 可行性 | ★★★★★ | ★★★★ | ★★★ |
| 收益（官方分） | +2~4 题 | +4~6 题 | +3~5 题 |
| 风险 | 极低 | 中（识别错题） | 高（重构回归） |
| 改动量 | 小（~40 行） | 中（~110 行） | 大（~170 行） |
| 验证成本 | 低（小批 20 题） | 中（30+ 用例 + 全量） | 高（全量 + 边界） |
| 提交窗口匹配（今晚 24:00） | ✅ 赶得上 | ⚠️ 勉强（需压缩验证） | ❌ 赶不上 |

**推荐：方案 A 今晚提交（24:00 窗口），方案 B 下一轮（验证充分后再上）。**

理由：
1. **提交额度宝贵**（单日 2 次）：今晚的窗口必须交给"低风险高确定性"的修复——A 的截断雪球消除是 100% 确定的收益（203→90 截断），且不引入任何新失败模式；
2. **B 的 sympy 中文识别风险不可控**：识别错题会制造"确定性错误答案"，若今晚仓促上，可能抵消 A 的收益甚至倒退——必须 30+ 用例验证后才能上，适合下一轮（明天 12:00 或 24:00 窗口）；
3. **C 是自杀式**：提交前全量验证都来不及，重构核心链路 3 天，等有完整验证周期再说（若冲刺更高名次，作为 V2.7 的储备）。

**A 的落地顺序**（今晚）：A1→A2→A3（10 分钟）→ A4（30 分钟）→ A5 lagent 摸底（1 小时）→ 本地小批 20 题验证（30 分钟）→ 全量 112 题验证（45 分钟，如时间允许）→ 提交。

## 实施记录（2026-08-20 晚）

### ✅ A1/A2 已落地（config.py）
- `truncation_continue_tokens` 2048 → 4096，新增 `truncation_continue_tokens_hard` 8192
  （reasoning 主链路续写用 8192，其余 4096）
- `truncation_continue_max_rounds` 2 → 1（消除续写雪球；一次续写不够走压缩重试）

### ✅ A3 已落地（utils/llm_retry.py）
- `_looks_truncated` 写满判据改用 `effective_cap = min(max_tokens, 4096)`——
  官方 client 若 clamp max_tokens 到 ≤4096，弱信号仍能触发（否则传 12288 而官方
  实际 4096 时截断被漏判）；官方未 clamp 时长答案多一次续写检查，无害。

### ✅ A4 核查结论（无需代码改动）
- 主推理路径三处压缩重试触发（传输失败 / `_looks_token_exhausted` / 客观题两次
  解析失败）**全部是异常/失败路径**，正常完成（`_is_complete`）直接返回——
  现有实现已满足"仅异常触发"，不做无谓改动（增量增强原则）。

### ✅ A5 lagent 摸底（真实 API 探测，2026-08-20 晚）

- **max_tokens=128：生效**（finish=length, ct=128）
- **max_tokens=4096/12288 长输出探测**：结果待后台任务回报（判定是否 clamp）
- lagent==0.5.0rc3 隔离环境安装中（依赖重：jupyter/ray/arxiv 等）

### ✅ 12 题真机验证（2026-08-20 晚，长证明 6 + 推导 2 + 计算 4）

### ✅ B1 sympy 自然语言化已实施（V2.6 追加，2026-08-20 晚）

用户拍板实施 B（sympy 自然语言化），自审后**做 B1、不做 B2**（B2 python 反哺
现有仲裁链已覆盖，额外改动风险大于收益）。改动集中在 `utils/sympy_pre_solver.py`：

| 改进 | 说明 |
|---|---|
| 模幂中文 | "求 2^100 除以 13 的余数"/"求 3 的 10 次方模 11 的余数"（"除以"必须配"的余数"，防把除法当取余） |
| 同余括号修复 | "3x ≡ 7 (mod 11)"（原正则 `\b` 后跟字母不匹配数字，括号形态漏识别） |
| 同余中文 | "5x 同余 3 模 7" |
| 组合数 | "求 C(10,3)×3^7 的值"——C(n,k)→binomial 翻译 + Unicode 乘号 ×·→* |
| 导数中文 | "求 x^2+1 的导数"（无 f(x)= 前缀） |
| 算术后缀 | "计算 2+3 的值/结果" |
| Unicode ∫ / 裸 lim | "求 ∫_0^1 x^2 dx" / "求 lim_{x→0} sin(x)/x" |
| **convert_xor 修复** | sympy parse_expr 默认对纯数字把 ^ 当 Python XOR——"C(10,3)×3^7" 曾被算成 367=(360 XOR 7)，加 convert_xor 后 ^ 恒为幂。这是**潜在老 bug**（裸算式 2^100 走 pow 不受影响，但 _parse 路径的 x^2 类表达式纯数字部分受影响） |

**验证**：
- B1 专项 33 用例（23 识别 + 10 拒绝）**全部通过**
- 154 项单测回归**全绿**（convert_xor 无破坏）
- **12 题真机 + LLM 判分：correct 9 + partial 1 + wrong 0（含 partial 83.3%）**
  - **5/6 B1 识别题 sympy 短路且全部 correct**（C(10,5)、2^100 除以 13、
    7^2024 除以 15、3x≡7 mod 11、x^3+2x 导数）
  - 对照题 5 correct + 1 partial（Banach 长证明本地截断，结论对、缺唯一性证明）
  - 命中率：识别题 5/6（83%）、全题集 5/12（42%）vs 之前 1/112（1%）
