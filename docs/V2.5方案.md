## 二、V2.5 第二批：判分口径对齐（基于官方原文）

### 2.1 官方判分口径三条铁律（原文摘录）

> ① "选择、填空题可简洁作答，**证明题和需要推导的题目应在 final_response 中保留必要过程**"
> ② "**证明题应给出必要且完整的证明过程**，其他需要推导的题目也应保留支撑结论所需的关键步骤"
> ③ "证明题或解析类题目，会**同时考虑结论和必要的推理过程是否合理**"

### 2.2 当前实现的缺口

核查代码后，当前对"推导题（computation）"的 final_response 是：
```
最终答案：xxx
关键步骤：步骤1…步骤2…步骤3…
```
关键步骤来自 `attach_steps`（只保留步骤标题+定理，**不保留计算过程细节**）。

**潜在风险**：官方 judger 对"推导题"要求"保留支撑结论的关键步骤"，而我们的 `build_steps_block` 做了**压缩**（每个步骤只留标题+定理名，`_condense_step` 把 LaTeX 计算过程都删了）。官方 judger 看到的可能是"结论对但过程被抽空"，判 partial 甚至 wrong。

### 2.3 改进动作（第二批）

| 动作 | 内容 | 收益 | 风险 |
|------|------|------|------|
| B1 | `_condense_step` 从"只留标题+定理"改为"标题+定理+**关键计算式**"（保留 1-2 个关键 LaTeX 式子） | 推导题过程更完整，judger 能看到支撑 | 答案变长，但 token 已上调（方向1）覆盖 |
| B2 | 证明题 `build_proof_body` 已保留完整过程，但需**核对是否被 `_MAX_PROOF_BODY_CHARS=4200` 截断**关键结论 | 防证明过程被截断 | 低 |
| B3 | 官方样例 final_response 是裸答案（"72"），但我们输出"最终答案：72 + 关键步骤"。**两种格式都合法**（官方原文只说"可简洁作答"），保持现状即可，不动 | — | — |

## 三、V2.5 第三批：retry_count=0 的深挖

官方日志里 `retry_count=0`（892 次请求**从未重试**），这暴露一个信号：

- 我们的 `chat_compatible` 三级探测 + `llm_max_retries=1`，意味着**传输失败只重试 1 次**。
- `retry_count=0` 说明**没有一次调用触发过重试**——要么官方 client 很稳定（好事），要么**我们主动关闭了重试**（`max_retries_per_node=1` + `llm_max_retries=1`）。

**但注意**：V2.1 就是因为重试太多次导致超时崩盘（19 error）。所以"重试少"是**正确设计**，不是 bug。**这一批不做改动**，仅记录：当前"快失败快降级"策略是对的，retry_count=0 是健康的。

## 四、V2.5 第四批：本地 400 故障的防御（v25 实测发现）

v25 求解时 11 题遭遇 400 Bad Request（分类 confidence=0.0、reasoning/python 全失败），最终 fallback 成"解题过程中出现错误"。虽然是本地 API 流控，但**官方评测也可能遇到同样的流控**。

| 动作 | 内容 |
|------|------|
| C1 | 分类器 confidence=0.0 且 difficulty 为空时，**不要直接放弃**，改为用默认 difficulty（medium）+ 默认 category 继续走求解，而不是 fallback 空答案 |

**收益**：官方评测若遇流控，这 11 题类场景能救回部分（当前是 0 分兜底）。
