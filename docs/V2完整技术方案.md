## 〇、比赛理解（方案的事实基础）

| 约束 | 数值 | 对方案的硬约束 |
|---|---|---|
| 题量 | 112 题（私有闭源，18 领域，CMO 级超难题） | 必须全覆盖 |
| 单题硬限 | 20 分钟 | 每题必须产出非空 final_response |
| 全卷上限 | 6 小时 | **平均每题预算仅 193 秒**（6h÷112÷并发3 之外的全局约束） |
| 并发 | 平台统一（约 3） | 无法自行扩容 |
| API 流控 | RPM 30 / TPM 150000（官方 client） | 单题 LLM 调用 ≤20 次、token 预算受限 |
| 判分 | 官方 judger 模型判 final_response（100 分制） | 形式与内容都重要 |
| 榜单基准 | 实时排名有 50+ 分队伍 | V2 目标 ≥ 榜一水平 |

**核心矛盾**：科研级超难题（单题天然需要 15-20 分钟深思）vs 全卷 6h（平均 193s/题）。
**解法**：不能"每题死磕"，必须**分级投入**——绝大多数题快速产出可靠答案，
把省下的时间集中给少数真正需要深思的题。

## 一、V1 官方评测诊断（14.29% 根因，V2 必须解决）

### 1.1 官方日志事实（eval_log_c0a00cb…）

```
agent stage: 21:11 → 08:30（11h19m，远超 6h 上限）
accuracy: 0.1429（16/112）· status: degraded · runner stage failed
```

### 1.2 根因链（三层叠加）

| 层 | 根因 | 证据 |
|---|---|---|
| **L1 完成率崩塌** | 超难题单题 15-20min，112 题全死磕 → 6h 只够解 ~16 题 | 16/112 = 14.29% |
| **L2 平台降级** | degraded + runner failed → 部分题未被正常判分 | status: degraded |
| **L3 资源过耗** | 24576 max_tokens 全量思维链 × 大量题 = 烧穿 6h | 11h19m 远超 6h |

**结论**：V1 是"每题都要完美"的架构，在超难题 + 6h 硬约束下必然失败。
V2 必须**重构为"全卷完成率优先 + 分级资源投入"架构**。

## 二、V2 架构总设计：三级投入漏斗

```
                    ┌─────────────────────────────────┐
   112 题           │  L0 快速通道（~70% 题）          │
 ──────────► 分类   │  规则+轻量验证，~60-90s/题       │
   预分类画像        └──────────┬──────────────────────┘
                                │ 需深思
                    ┌───────────▼──────────────────────┐
                    │  L1 标准通道（~25% 题）            │
                    │  双路径+符号验证，~180-300s/题     │
                    └───────────┬──────────────────────┘
                                │ 仍不确定
                    ┌───────────▼──────────────────────┐
                    │  L2 深度通道（≤5% 题，保底机制）    │
                    │  多候选+Playoff+审计，~600-900s/题 │
                    └──────────────────────────────────┘
```

**核心原则**：
1. **完成率优先**——每题必答（L0/L1/L2 都有兜底），宁可少验证不可空卷
2. **资源分级**——把 6h 预算按"题目的深思需求"分配，而非平均
3. **动态调控**——题间预算池实时监控，超支自动降级通道

## 三、V2 六大核心机制（可落地）

### M1【全卷完成率引擎 PaperPacer】—— 解决 L1（最重要）

**问题**：V1 每题 1200s 预算，112 题 × 平均 6min = 烧穿 6h，只完成 16 题。

**设计**：新增 `utils/paper_pacer.py`，全局节奏控制器：
1. **题间预算池**：以 `6h ÷ 112 = 193s/题` 为基准线，动态计算剩余可花时间
   ```python
   remaining_budget = (6h - 已用时间) / 剩余题数
   ```
2. **分级预分配**：分类后按难度/题型给每题预算
   - easy/客观/概念题 → 60-90s（L0）
   - medium → 180-300s（L1）
   - hard → 600-900s（L2，仅 ≤5% 题）
3. **超支护栏**：若预估"当前节奏会答不完"，自动把剩余题预算整体下调，
   **保证 112 题全有答案**——完成率 100% 时哪怕 50% 正确也有 50 分
4. **快慢分离**：L0 通道题省下的时间**滚动进预算池**，供 L2 深思考

**成本**：纯规则计算，零 API。**收益**：完成率 16/112 → 112/112（+100% 覆盖）。

---

### M2【最少资源高准确率：轻量预验证 + 置信门控】—— 解决"最少资源"

**问题**：V1 每题全链路（双路径+Python+Playoff+Critic）≈ 12 次 API/题，太贵。

**设计**：新增 `utils/confidence_gate.py`：
1. **分类置信度**：分类节点顺带输出 confidence（已有雏形）
2. **置信门控**：
   - confidence ≥ 0.9（且是常规题型）→ **L0 快速通道**（单路径 + 规则校验，~3 次 API）
   - 0.7-0.9 → **L1 标准通道**（双路径 + 符号验证，~6-8 次 API）
   - < 0.7 或超难特征 → **L2 深度通道**（全链路，~12-15 次 API）
3. **资源审计**：每题记录实际 API/时间/token，超支自动降级

**收益**：平均 API 次数 12.2 → **~5-6 次/题**（资源减半），单题耗时 189s → **~120s**，
把省下的资源全部用于 L2 深思考（或提高完成率安全边际）。

---

### M3【科研级超难题专项：DeepSolver 深思考通道】—— 解决"95%+ 准确率"

**问题**：超难题需要 15-20 分钟深思，但 6h 只够 16 题死磕。V2 用"少数题深思考"替代"全部题浅尝试"。

**设计**：新增 `nodes/deep_solver_node.py`（L2 通道核心）：
1. **多候选生成**：3 个独立推理路径（方法 A 直接法 / 方法 B 构造法 / 方法 C 反证法），
   每个候选带 confidence 自评
2. **候选代回核验**（V1 Playoff 升级）：对数值/计数/方程题，把候选**代回题面条件**
   做确定性验证（沙箱执行，≤60s）
3. **组合裁决**：多数一致 → 采纳；分歧 → 逐一代回 + 符号约定检查
4. **过程审计**（复用 V1 Critic）：完整性 + 计算抽核

**成本**：仅 ≤5% 题触发，每题 600-900s（占全卷 ≤10% 时间预算）。
**收益**：把 V1 的 16 道深思考题，换成 **"100 题快速可靠 + 12 题深思考"** 的分配，
总正确率大幅提升。

---

### M4【答案形式对齐 + 符号约定显式化】—— 解决 judger 形式失分

**问题**：V1 idx=94 答对数学但形式不合（区间 vs 半长）→ partial。

**设计**：
1. `utils/form_align.py`：题面"求 X"形态解析 → 检测答案形式错配 → 低成本重述（~512 token）
2. `utils/sign_convention.py`：曲率/法向等约定敏感词 → 答案中显式注明约定

**成本**：仅错配触发（~5% 题），每次 ≤3s。**收益**：partial → correct。

---

### M5【token 预算全局管控：防烧穿】—— 解决 L3

**问题**：24576 max_tokens 全量思维链 × 大量题 = 资源爆炸（11h19m 实证）。

**设计**：
1. **max_tokens 分级**（已部分落地）：
   - reasoning: 24576 → **8192**（已完成）
   - 新增：L0/L1 通道用 4096，仅 L2 深思考用 8192
2. **token 池监控**：`TokenBudget` 升级为全卷级（6h 内总 token 上限），
   超支自动降级通道
3. **预填充加速**：分类/仲裁等短调用继续用 prefill（~1s），不烧 token

**收益**：token 消耗降 3 倍，资源开销降至 V1 的 1/3。

---

### M6【平台环境防御加固】—— 解决官方环境差异

**问题**：官方 client 与本地有差异（限流/超时/负载），曾导致评测异常。

**设计**：
1. `utils/client_tuning.py` 已实现（120s→780s 超时调优，best-effort）——**保留**
2. **自适应重试**：RPM 限流 429/配额错误 → 指数退避 + 降速（避免被打死）
3. **异常兜底强化**：任何节点失败 → 立即产出"当前最佳答案"而非空卷
   （V1 已有应急直答，V2 强化覆盖到每个节点）
4. **平台仿真测试**：模拟官方 exec 加载（无 __file__）、限流、超时场景

## 五、实施路线（分 3 个 Sprint，每步可验证可回退）

```
Sprint 1（1-2 天）：完成率地基 —— M1 + M5 + M6

  · 验证：112 题 mock 压测（全卷完成率 100%，0 超时）

```

**总工期**：4-7 天（含真机验证）。每 Sprint 独立交付、独立验证。
