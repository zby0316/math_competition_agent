## 一、功能缺口清单（对照"顶尖"逐项评估）

### G1. 问题分解 / 子问题管理 —— ❌ 缺失（不值得加完整版，值得加轻量版）
- 现状：`hard_plan_hint`（utils/hard_plan.py）只有"单次调用内 目标锚定→路径规划→逐步求解"
  的提示词，无真正的子问题状态管理、无引理库、无子目标追踪。全图把整题交给一次 12288-16384
  token 的推理调用。
- 顶尖做法：MCTS/分层分解（AlphaProof 式），把题拆成可验证的子目标并逐步验证。
- **是否值得加**：完整版（子问题状态 + 子目标验证回环）在"单题 20min + 官方慢 API"下不可行
  ——每次子问题求解都是一次 77-552s 的完整调用，分解 3 个子问题 = 必超时。轻量版（在
  hard 推理提示中强制"把目标分解成 ≤3 个可独立核验的子断言，最后逐条回代"）已被
  hard_plan 七点部分覆盖。**结论：不加**，保持现状即可；资源应投在 G9/G10。

### G2. few-shot 范例库 —— ❌ 缺失（值得加，但要克制）
- 现状：`skills_loader` 提供 18 科 `*skill.md`（课程知识）+ `*验证示例.py`（验证代码示范），
  `competition_methods` 提供 10 类方法的"求解框架提示"（方法步骤，非例题）。**没有一条
  "相似题完整解法示范"（题目→正确解答→关键技巧）被检索注入**。
- **是否值得加**：合规允许（纯提示内容，非训练）。收益中等——intern-s2 自身推理能力强，
  范例对 hard 竞赛题（函数方程、几何构造）的增量主要在"示范解题套路"，而 competition_methods
  已静态覆盖套路。风险：锚定效应（示范解错或示范题与本题相似但不同，会带偏采样）。
  **结论：低优先。** 若做，只做"2-3 条/方法 × 10 方法"的小型人工精炼库，仅注入 SC 的
  construct 视角（采样场景，锚定危害可控），不进主路径。

### G3. 过程奖励逐步验证（PRM 式） —— 🟡 部分有（不值得做完整版）
- 现状：`critic_node` 对 1-3 个关键中间计算做 LLM 抽核 + `derivation_conflict` 正则自检
  （同变量两值矛盾）+ `proof_deepener.proof_self_critique`（M12 全文审稿）。这是"轻量逐步
  核验"，但抽核数量少（1-3 个）、且只对 final 候选执行。
- 顶尖做法：PRM 对每一步打分（需训练，违规）；AlphaProof 用验证器逐步校验（需 Lean，违规）。
- **是否值得加**：完整逐步验证在"无训练/无 Lean"约束下只能退化为"LLM 逐步骤自检"，成本高
  （每步一次调用）收益不稳。**结论：不加**；把 G3 的增量并入 G10（critic 增强）。

### G4. 反例引导搜索 —— 🟡 工具已建、生产链路未接（**值得加，最高性价比之一**）
- 现状：`answer_verifier._ALTERNATE_VERIFY_PROMPT` 内置"反例搜索"验证模式；
  `utils/verifier_feedback.py`（V5.0 验证 FAIL → 反例提取反馈）**只在 local_test/deep_water_solver.py
  实验管线中使用，生产图（nodes/）零引用**——是明确的"看似有但没用上"。
- 顶尖做法：AIMO2 金牌管线"采样→程序化验证→反例反馈→重采样"闭环。
- **是否值得加**：**值得**。SC 的 verify 阶段目前"FAIL 即不锁"，反例信息被丢弃；
  把 verifier_feedback 接进 SC——verify FAIL 时提取反例，做**一次**带反例的定向重解
  （复用既有 reserve_margin 定价），预期对 hard 计算题有 1-2 题/轮级救回（deep_water
  实验已证该回路有效）。成本低（代码已存在，只是接线）。

### G5. 符号化简预处理器 —— ✅ 已有（值得小幅增强）
- 现状：`sympy_pre_solver` 覆盖算术/同余/模幂/导数/定积分/极限/方程/矩阵，且带
  约束词守卫（正根/整数解等不短路）、近似算法守卫、未定值泄漏守卫——设计成熟。
- 缺口：只做"整题短路"，不做"题面表达式化简后再喂 LLM"（如把题面内嵌的长式子
  simplify 成规范形）。**是否值得加**：收益低（模型自身可处理），且化简改写题面有
  改写错误风险。**结论：不加**，现状已超出同类系统。

### G6. 题型专门化解法器 —— 🟡 客观题强、难题弱（值得加：主路径方法路由）
- 现状：客观题极强——choice/true_false/fill 专用提示、性质判断题判定、空位计数、
  实算填空升级双路（verify_router）、判断题双向确认（judge_confirm）、计数枚举守卫、
  F₂/Z_m 模结构守卫。计算题有 hard_plan 七点 + counting/modular guard。
- 缺口：`competition_methods`（10 类竞赛方法）**只注入 SC 的 construct 视角**
  （sc_consensus_node L283-292），主推理路径的 hard 题只有通用 hard_plan；函数方程、
  极值/最优化、平面几何这三类最高难领域没有主路径特化提示。
- **是否值得加**：**值得**。把 `route_competition_method` 注入主推理路径的 hard 分支
  （与 hard_plan 并列，零额外调用成本），并把函数方程（换元族）、极值（构造+界闭环）
  两条新方法加入 _METHODS 与 CATEGORY_SPECIFIC_HINTS。

### G7. 答案形态自动检测 —— ✅ 已有（仅剩 computation 多值形态一个口子）
- 现状：`form_align.expected_form`（choice/judge/fill/single/interval/enum）+ `problem_profile`
  （多问项/全部解/极值/开区间/序数/可行性+计数）+ `normalize_objective_answer` + `count_blanks`
  ——比多数同类系统完整。
- 缺口：computation 题的"集合/多值/有序对"形态（如"列出所有三元组"）无专门形态检查，
  依赖 answer_contract 的 enum 组件。**是否值得加**：小成本可并入 G9 的确认流程。
  **结论：小幅增强**。

### G8. 多题间知识复用 —— ❌ 缺失（合规范围内价值低，不建议）
- 现状：PaperPacer 只做**预算**复用（全卷完成率引擎），无答案/方法跨题复用。
- 合规：官方明确"每 problem 按独立题处理"；跨题抄答案是作弊红线。方法级经验
  （"上一题这种结构用了换元"）作为提示知识理论上合规，但 112 题彼此独立、动态
  注入收益不可测。
- **是否值得加**：**不加**。静态方法库（competition_methods）已是合规边界内的最优解。

### G9. 匹配答案的确定性再确认（反"同源一致错"）—— ❌ 结构性空白（**最值得加，第 1 优先**）
- 现状：整个验证梯（SC/playoff/双验证/复核投票）**全部只在 non-match 时触发**
  （`_wants_sc` 明确 `validation_status in ("match", None)` 即跳过；playoff/双验证在
  mismatch/uncertain/contradict 分支）。match 出厂 = "推理与 Python 一致"即放行，
  **没有第三方独立证据**。round_log 实证：easy 仅 50%，"#0/#29 同源同错 match 锁错"、
  "双闭式等价 6/6 同错（同源陷阱）"——主路径与 Python 都是 397B 生成，会**一致地错**。
- 顶尖做法：AIMO2 的"验证器 > 投票器"原则——**任何候选（含 match 候选）都过程序化验证**。
- **是否值得加**：**最值得**。对 match 的计算题（闭式答案）当 `remaining_hard > 700s` 时
  跑一次 `verify_candidate`（2 份独立验证代码，~2-3min，easy/medium 快速路径后通常有预算）。
  V4.1 回放已证明"双闭式等价不可信、双独立代码等价才可信"，把这条纪律从 non-match
  扩展到 match，直接收复"match 锁错"失分——这可能是当前结构下最大的一块可收复分。

### G10. 证明题验证真空 —— 🟡 空白（值得加轻量数值抽核）
- 现状：证明题 python 无验证能力（playoff 对证明题稳定 INCONCLUSIVE"不是故障"），
  正确性完全依赖单次推理 + critic 的 1-3 个计算抽核 + M12 自检。**没有对证明中
  间断言（引理/构造）的逐条数值/反例抽核**。
- **是否值得加**：**值得（轻量）**。在 critic 对证明题增加"对 2-3 个可数值化的中间断言
  生成微型验证代码"（如群阶、收敛半径、不动点数值），成本 ~2 次短调用，能把"证明
  过程错但结论碰对"的题拦下。注意预算门控（复用 critic_reserve_margin_s）。

### G11. MCTS / 搜索式推理 —— ❌ 缺失（约束下不可行，明确不加）
- 现状：local_test/mcts_experiment.py 有实验，生产无。无训练 + 官方慢 API + 单题 20min
  下，MCTS 的每节点一次完整推理 = 指数级时间。**结论：不加**。

### G12. 题目重述核对（paraphrase check）—— ❌ 缺失（小成本，可选）
- 现状：跑题检测（off_topic_guard）只做"答案与题面实体词交集"，放弃重读只处理
  "无法确定"类；**没有"把题面要点复述回来核对"的机制**（模型理解错题面的检测）。
- **是否值得加**：低优先。hard 推理提示可加"第一步用一行复述题面要求"，若复述与
  题面目标错位则触发重读。成本≈0，收益不可测。**结论：可选**。

## 三、机制协同分析（冲突 / 重复 / 空白）

### C1. 验证梯整体结构（正确部分）
match → critic；mismatch/contradict → playoff（确定性优先）→ 双验证（V4.1/V4.7）→
仲裁（既有候选）→ 重算（换方法）——"确定性 > 采样"的优先序设计正确，V5.3 的
三处 latch（sc_consensus_done / second_python_done / playoff_trace 防重入）把
历史上"SC 每轮重跑""双验证三入口连跑 3 份代码""playoff 死循环"三个预算烧穿
点都修掉了。这部分是健康的。

### C2. 冲突：hard 计算题的"三重复采样"（V2.5 投票 + diverse B + SC）
- 同一类题（hard 计算题、未 match）会依次消费：
  ① 首轮 main 推理内部 `_sample_vote_reasoning`（3 温度采样，V2.5）+
  ② 并行扇出 diverse B 路径（1 次完整推理）+ ③ 未 match 后 SC（6 视角 + 3 代码 +
  交错 + 验证 ≈ 最多 14 次调用）。
- 三者目的相同（打破单样本随机性），粒度不同但**成本线性叠加**：hard 题首轮即
  5 次推理调用，SC 再 14 次，轻松逼近 hard 上限 24——reconciliation 重算轮几乎无配额。
- **建议**：二选一收敛——(a) 首轮采样投票命中 2/3 即跳过 SC 的推理视角（共享采样）；
  或 (b) 首轮不投票（SC 已覆盖采样职能），把配额留给 SC 的代码通道与验证器。
  按 round_log，SC 是救回率最高的机制，建议保留 SC、弱化首轮投票。

### C3. 冲突：SC 调用量与难度调用上限（easy≤10）未联动
- `_wants_sc` 只查 `remaining_hard > 600`，不查 `clock.llm_call_count()` vs
  `max_llm_calls_by_difficulty`；而 easy 题 SC 又被 V5.1 恢复触发。easy cap=10，
  SC 单阶段最多 ~14 次调用——超帽后 `llm_retry` 抛 DeadlineExceeded，SC 循环 catch
  后静默降级，**已花的调用白烧、cap 形同虚设**。**建议：SC 触发前用
  `clock.llm_calls_exhausted()`/剩余配额门控，与 cap 联动。**

### C4. 空白：match 无独立确认（=G9，协同层最大空白）
- 验证梯只保护"不一致"的题；"一致但同错"的题（easy 一半错误的主要形态）没有任何
  机制覆盖。SC/playoff/双验证全都够不着它。这是**结构性盲区**而非参数问题。

### C5. 空白：证明题验证真空（=G10）
- 证明题在整个验证梯里只能走到 critic 的 1-3 个抽核 + M12；playoff/SC/双验证
  对证明题全部自动失效（SC 直接 `question_mode == "proof"` 返回 False）。无
  "证明中间断言数值抽核"通道。

### C6. 空白：SC verify 阶段与双验证目的重叠、预算双花风险
- SC 的 `verify_candidate`（2 份验证代码）与 cross_validator 的双验证（2 份独立代码）
  功能高度同构，但属于不同阶段、不同 latch（second_python_done vs SC 内部），
  同一题可能两处各花 2 次代码调用。**建议：SC 触发前检查 `second_python_done`，
  已双验证过则跳过 SC 的 verify 子阶段（保留投票）。**

### C7. 已修复的历史冲突（记录，勿回退）

- coordinator 证据闸门 vs playoff decisive（已豁免）；

- 这些 latch 依赖 `state` 字段的隐式传递（如 give_up_forced_sc 藏在
  validation_details 里、repair_hint_source 一次性消费），脆弱但已工作；若重构，
  建议收进一个显式 `mechanism_flags` 字段。

### 已完备的（不建议再动）
- 客观题全链路（识别/归一化/空位/双向确认/形式对齐）——同类系统顶级；
- 时间预算体系（PaperPacer 全卷 + 难度软预算 + reserve 配额 + 调用上限）——完备；
- 截断/超时/传输故障韧性（压缩重试/续写/捞回/应急直答）——完备；
- 确定性验证阶梯（sympy 短路/对拍/playoff/双验证）——完备；
- 合规面（仅官方 API、无训练、无 Lean、零外部调用、仓库自检）——完备。

### 不完备的（按对 112 题总分的影响排序）

**最缺的 3 个功能：**

1. **匹配答案的确定性再确认（G9）** —— 影响面最大。
   证据：官方 54.46% 中 51 错题；本地 round_log 反复出现"match 锁错/同源同错"
   （#0/#29 easy 同错、双闭式等价 6/6 同错）。当前验证梯 100% 集中在 non-match 分支，
  而 easy/medium 的主错误形态恰恰是"双路一致地错"。实现：match + 闭式 + 
  `remaining_hard > 700s` 时跑 `verify_candidate`，双 PASS 才锁、单 PASS 仅提示。
  成本可控（2 次短调用），预期收复 easy/medium 数个百分点的失分。

2. **反例反馈回路接入 SC（G4 / R1）** —— 影响 hard 深水区。
   `verifier_feedback` 已写好但从未进生产。SC verify FAIL 时把反例喂给一次定向
   重解（而非丢弃），补上"采样→验证→反例→重采样"闭环的最后一环。deep_water 实验
   已验证该回路有效（#0/#2/#5 等）。成本：每失败候选 +1 次调用，受 sc_end 门控。

3. **主路径竞赛方法路由 / 题型特化（G6）** —— 影响 hard 高难领域。
   `competition_methods` 只进 SC 的 construct 视角；主推理路径的 hard 题（函数方程、
   极值、几何构造）没有方法框架。把方法路由注入 hard 主路径（零额外调用），并补
   函数方程/极值两条新方法。这与 G9/G4 无冲突、独立生效。

**次要补强（可选）：**
- G10 证明题中间断言数值抽核（critic 增强）；
