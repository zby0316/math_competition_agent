## 发现

1. `eval_local.grade` 对六题均报错：它直接比较含“关键步骤”的中文输出与英文自然语言参考答案，无法可靠评测这组题。应先修正答案抽取和结构化比较，再用自动正确率筛选策略。
2. `idx=20` 的 Python 分支成功运行，却输出 `nan`，同时宣称 `FAIL`。`parse_verification_evidence` 将其视为真实矛盾，触发额外求解和仲裁。最终仲裁选回正确答案，但该题耗时 **327.35 秒**，为六题最高。非有限结果应按“无法判定”处理，除非另有独立、可核实的反例。
3. 前五题内部验证状态均为 `uncertain_arbitrating`，即使推理与 Python 的答案数学上相符。这提示候选答案的表达方式和比较逻辑还会产生不必要的仲裁；需要在更大样本上确认影响。

建议先处理第 2 项的错误证据，再完善诊断集的判分。两者目前都是风险定位，尚无证据表明改动后官方分数必然上升。

- 用本次 `idx=20` 保存的真实 Python stdout 离线重放：旧路由 `mismatch_arbitrating`，新路由 `uncertain_arbitrating`；`answer=None`、`contradictions=[]`。这验证了原始故障路径不再把 `nan` 当反证。
- 单题在线回归：最终答案仍为 `ln(2)/2`，耗时 **289.17 秒**，内部状态为 `match`。此次模型直接生成了有效的 Python 答案，没有重现 `nan`，因此 **不能**把比原来少的约 38 秒归因于修复。

## 下一项提分风险：仲裁候选的完整性

原始六题 trace 中，前五题都进入了 `uncertain_arbitrating`，即使 Python 验证报告 `support`。其中两题的 Python 答案只覆盖部分要求：`idx=8` 的原函数缺少积分常数 `+C`；`idx=16` 只给出一个主值解，缺少整数周期参数。最终仲裁均选了较完整的推理答案，所以这六题没有实际失分；但如果类似场景选了不完整候选，就存在失分风险。建议下一步先为积分常数、通解参数和多问字段增加候选完整性检查，再评估是否减少不必要的仲裁调用。当前还没有官方逐题结果，风险等级属于基于本地 trace 的推断。

### 候选完整性保护的离线回归

现已扩展候选契约：无界积分要求积分常数；无指定区间的三角方程要求周期解集；显式编号、带名称的多问要求各字段均有值。用原试跑题面与两侧答案回放，若强制选中 `idx=8` 或 `idx=16` 的 Python 候选，契约会改选完整的推理候选；`idx=12` 的四项参考答案和两侧原候选均通过检查。24 个公开题参考答案也均通过新契约检查。

为避免格式规则盖过明确数学反证，有未解决的验证矛盾时不自动改选；两份候选缺同一项、或替代候选只是缺项数量较少但覆盖并非严格更多时，也保持仲裁原选择。这是离线保护回归，尚未证明官方得分变化，也没有新增模型调用。
